# 학생용 캘린더·D-Day 설계 문서

작성 기준: 2026-10-03, Asia/Seoul

## 목적과 읽기 순서

맥과 아이폰에서 연결되는 개인 할 일·캘린더·D-Day 도구를 설계한다. 홈은 월간 할 일을 중심으로 하고, 임박 기간 최대 세 개를 작고 간결한 보드 카드로 보여준다. 추가 기간은 캘린더를 밀어내지 않는 그림자 오버레이로 연다. 자동 회전 없이 선택일 목록의 단일 추가 버튼, 앱명/검색이 없는 화면, 중앙 아이콘 하단 내비게이션을 사용한다. 과제·논문 제출 같은 마감과 수강신청·티켓팅의 시작을 구분하며, 기간 경과와 하위 할 일 완료를 혼동하지 않도록 한다. 실제 초기 사용량은 본인 한 명이지만 다른 계정의 데이터 격리를 포함한다.

## 확정된 기준

- Next.js 16 정적 내보내기와 Firebase Hosting/Auth/Firestore **Spark**를 사용한다.
- macOS 웹/PWA와 iOS 홈 화면 PWA로 시작하고 네이티브는 후속 단계에 둔다.
- 한국어, Google 로그인, `Asia/Seoul`이 기본값이다.
- 홈은 **월간 할 일 화면**이며 날짜별 하루 할 일과 가장 임박한 기간형 항목 최대 세 개를 카드로 보여준다. 항목은 자동 회전하지 않으며 초과 기간은 달력을 밀지 않는 오버레이로 확인한다. 기간 바에는 양 끝 날짜/시각만 두고, 날짜별 완료는 할 일 목록 체크박스로 처리한다. 전체 주간·월간 일정 캘린더는 별도 페이지다.
- 고정 수업·미팅은 TodoMate식 날짜 중심 캘린더에서 관리한다. 홈/캘린더는 중앙 하단 아이콘으로 이동한다. 기간 바는 **시간 경과율**이며 하위 할 일 완료는 바 옆 텍스트로만 표시한다.
- 기간형 항목은 시작 카운트다운과 하위 체크리스트를 지원한다. 예정 상태는 파랑, 진행 중은 라벤더, 종료는 회색으로 표시한다. 시작 카운트다운 기본 노출은 시작 1일 전이다.
- 직접 입력·ICS 일회성 가져오기, 오프라인 작성·수정과 충돌 보존을 포함한다.
- V1은 전경 인앱 카운트다운·안내다. 닫힌 앱의 예약 푸시는 제공하지 않는다.
- 그룹·소셜·결제·학교 공지 자동 수집·외부 캘린더 양방향 연동은 후속 범위다.

## 문서 상태와 선택할 사항

제품 범위, 월간 할 일 홈 구조, 시간·동기화 기본값과 최신 보드형 홈 대안을 사용자와 확정했다. 캔버스 배경은 흰색이며 상태 구분에는 예정 파랑·진행 라벤더·종료 회색을 사용한다. Figma의 보드 비교는 데스크톱 1440×930이며 모바일은 기존 390×844 화면 흐름을 따른다. 시안의 날짜와 남은 시간은 예시이며 시간 계산·동기화·알림의 실제 계약은 제품/기술 문서가 기준이다.

구현 준비 자료는 [구현 문서 안내](implementation/README.md), [전체 구현 설계](implementation/05-implementation-design.md), [9단계 실행 계획](implementation/06-execution-plan.md)에서 읽는다. 기존 조사와 같은 방식으로 공식 출처·확인일·제품 판단을 구분하고, 최신 Figma를 조회한 화면과 핵심 동기화 계약을 연결했다. 새 기본값은 검토 제안으로 표시하며 앱 코드·패키지 설치는 아직 진행하지 않았다.

화면 자료는 `assets/references/`, 생성 시안은 `assets/concepts/`에 보관한다. 원본 출처와 생성 프롬프트·이미지 대응표는 [시각 자료 기록](assets/README.md)에 기록한다. 외부 제품 화면은 조사 참고용이며 앱 배포 자산으로 재사용하지 않는다.

## 결정의 권위와 변경 절차

제품 범위는 `02`, 타입·저장 계약은 `04`, 알림 규칙은 `05`, 수용 기준은 `06`을 기준으로 한다. 시각안의 장식이나 일부 누락이 기능 요구사항을 변경하지 않는다. 충돌하는 표현은 기능을 임의로 줄이지 말고 위 기준 문서를 함께 수정한다.

새 프로덕션 패키지는 `[ASSUMPTION]` 후보로 기록하고 구현 PR에서 논의한다. 현재 저장소에 앱 패키지나 코드가 없어 이 문서 작업에서 `pnpm test/typecheck/lint/build`가 통과했다고 주장하지 않는다. 앱 구현 때 네 명령의 성공이 완료 조건이다.

일반 구현은 `gpt-6-luna` + `xhigh`, 시간·Rules·오프라인 동기화의 어려운 계약은 주 에이전트가 맡는다. 현재 에이전트 도구에는 별도 fast 설정 인자가 없다. TDD는 어려운 작업에만 적용하고 일반 작업은 구현 후 필요한 검증을 추가한다.

## 조사와 작업 분담

경쟁 비교, UX·프론트엔드, Firebase 기술 초안은 사용자가 지정한 `gpt-6-luna` + `xhigh` 에이전트가 작성했다. 주 에이전트는 시간 의미, 무료 운영 경계, 동기화·충돌 계약과 문서 간 요구사항 연결을 검토한다. 시각안은 내장 Image Gen으로 별도 생성하며 텍스트 에이전트 모델과 동일한 모델이라고 주장하지 않는다.

공식 자료로 확인한 사실, 개별 사용자 후기, 이 제품을 위한 설계 추론은 구분한다. 모든 시장 자료를 빠짐없이 조사했다는 뜻은 아니며 관련 레퍼런스 범주와 접근 한계를 조사 문서에 명시한다.
