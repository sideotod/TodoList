# 대학생·대학원생 일정 관리 제품 조사

**조사 기준일:** 2026-10-03, Asia/Seoul
**조사 범위:** macOS/iOS와 웹에서 이어 쓰는 캘린더·작업 앱 7개, 한국 대학 맥락 및 D-Day/접수 창 참고 서비스 3개, 실제 학사·장학·연구 일정 공지 5건, 공식 티켓 예매 공지 1건, 대학의 시간 관리 안내 1건. 공개 제품 페이지와 도움말, 한국 App Store, 기관·예매사 공지만 사용했다. 앱 리뷰는 소수의 개별 의견으로 별도 표시했다.

## 제품 범위와 해석 기준

아래 비교는 이미 정해진 제품 범위를 기준으로 읽는다. 제품의 주 사용자는 한 명이며, 베타에는 서로 분리된 계정으로 친구가 들어올 수 있다. 첫 버전은 PWA로 macOS와 iOS에서 사용하고 네이티브 TypeScript 앱을 후속 경로로 둔다. Firebase Spark를 사용하며 결제는 현재 범위에 없다. 월간 할 일 홈의 상단에 기간 진행 정보를 두고, 전체 주간·월간 일정 탐색은 별도 캘린더 페이지에 둔다. 수동 입력 및 1회 ICS 가져오기를 지원한다. 작업 시간 진행 표시는 실제 경과 시간과 설정한 기간을 비교하고, 작업 내용의 완료율이나 퍼센트는 나타내지 않는다. 편집은 오프라인에서도 가능해야 하며 동기화 충돌 때 데이터를 덮어쓰지 않고 사용자가 보존할 항목을 선택한다. 첫 버전 알림은 앱을 열어 둔 상태에서 제공하고, 앱이 닫혀도 도착하는 푸시는 이후 단계다. 이 결정들은 조사 결과가 아니라 제품 소유자가 고정한 범위다.

여기서 “무료”는 서로 다른 세 가지를 구분한다.

1. 스토어에서 앱을 돈을 내지 않고 내려받을 수 있는가.
2. 로그인 후 주요 기능을 무료로 계속 쓸 수 있는가.
3. 모바일·데스크톱·웹의 데이터와 구독 권한이 계정 단위로 연결되는가.

앱 스토어의 무료 표시는 첫 항목만 확인한다. 로그인 후 유료벽이나 계정 간 구독 권한을 판정하지 않는다.

## 요약

현재 제품군은 캘린더와 일반 작업, 학생 전용 학사 일정, D-Day 표시, 공식 접수 포털을 각각 잘 다루지만, 이 네 가지를 한 사용자용 일정 공간에 합친 비교 제품은 조사 범위에서 찾지 못했다. TickTick·Todoist·Apple·Google은 기기 간 기본 접근과 알림을 제공하고, 일부 캘린더 보기·알림·작업 기간은 유료 플랜에 둔다. MyStudyLife는 수업·과제·시험에 가장 초점을 맞춘 제품이며, 과제의 부분 진행과 시험 카운트다운을 공식 안내한다. 한국의 학사·장학·연구 공지 표본에서는 마감일 하나보다 시작 시각, 종료 시각, 다른 서류 마감, 기관 승인 기간이 별개로 나타난다. 연세대 수강신청 예시에서는 본 신청이 오전 10시에 시작하지만 로그인이 오전 9시에 열리고, 한국장학재단 예시에서는 학생 신청 마감 뒤 서류·가구원 동의 마감이 이어진다. 이는 기간과 선행 알림을 분리해 다뤄야 할 근거지만, 학생 전체의 선호 빈도를 보여주는 사용자 조사 결과는 아니다. 투두메이트 Mac 앱은 한국 스토어에서 무료 다운로드로 표시되지만, 이는 로그인 후 무료 사용 범위나 유료 기능을 밝혀 주지 않는다. 사용자가 직접 겪은 데스크톱 유료 사용 경험은 그대로 동기로 남기며, 공개 자료로 유료벽·구독 권한은 확인되지 않았다.

### 해석할 때 지킬 경계

- **관찰된 사실:** 공고 페이지에 시작/종료 시각, 부속 서류, 후속 승인 기간이 별도로 기재되어 있다.
- **개별 사용자 의견:** Mac 리뷰의 유료 사용 언급, TodoMate의 진행 중 상태 요청, D-Day 요청은 각각 특정 날짜의 한 사용자 발언이다.
- **추론:** 사용자가 이러한 일정을 하나의 캘린더에서 관리하고 싶어 하는지, 어느 시점에 몇 번 알림을 원하는지는 아직 확인되지 않았다.
- **알 수 없는 것:** 투두메이트 Mac 유료벽과 구독 권한의 공식 규칙, ICS 가져오기 때 중복/충돌을 처리하는 실제 사용자 선호, PWA에서 앱이 닫힌 동안 도착하는 알림의 중요도는 공개 자료로 결론 내리지 않았다.

## 근거가 뒷받침하는 기회 우선순위

아래는 기능 구현 목록이 아니라 조사 근거에 따른 문제 우선순위다. 실제 선호는 사용자 검증이 필요하다.

1. **기간을 하나의 마감 시각으로 평탄화하지 않기.** 등록/신청 창, 보완 서류 창, 기관 승인 창, 온라인·인쇄본 제출 창은 종료 시각과 선후 관계가 다를 수 있다. 이 구분을 캘린더와 다가오는 일정에서 잃지 않는 것이 가장 강한 도메인 신호다. [R21–R24, R27]
2. **시작 알림과 마감 알림을 별개의 순간으로 다루기.** 연세대 수강신청 예시는 로그인 오픈과 신청 개시가 한 시간 차이고, KOSAF 공지는 09:00 개시와 마감일 18:00을 함께 적는다. 실제 알림 시점 선택은 사용자 검증 전까지 열어 둔다. [R21, R24]
3. **경과 시간과 작업 완료율을 시각적으로 혼동하지 않기.** 사용자 고정 범위는 시간 진행 표시이며 MyStudyLife의 부분 완료나 일반 작업 체크와는 다른 값이다. 공고를 향한 시간이 얼마나 지났는지와 과제 내용이 얼마나 완료됐는지는 라벨과 설명이 달라야 한다. 제품 고정 범위와 경쟁 제품 비교에서 도출한 판단이다. [R16, R21–R25]
4. **데스크톱 접근 정책을 가격 한 단어로 단정하지 않기.** 투두메이트 무료 다운로드는 공개 확인이지만 실제 데스크톱 유료 사용 여부는 미확인이다. 사용자 보고를 동기로 보존하고, 구매·로그인·기기 전환 경험을 별도 검증 대상으로 둔다. [R01–R03]
5. **동기화와 수동/ICS 입력의 안정성을 우선 검증하기.** 이는 고정된 제품 범위와 사용 시나리오에서 중요한데, 이번 경쟁 조사에는 오프라인 후 충돌 해결 방식의 충분한 사용자 증거가 없다. 오프라인 수정과 중복 가져오기는 사용자가 이해할 수 있는지 확인이 필요하다.

실행 순서는 첫 주에 시간 라벨·입력·충돌 비교의 작은 사용성 검증, 이후 분기 안에 Mac↔iPhone 베타와 알림 기본값 검증, 그 다음에 네이티브 알림·복잡한 반복·외부 연동 수요 조사를 권한다. 이는 인력이나 일정이 확정된 납기 약속이 아니라 조사 기회를 검증하는 순서다. 구현의 단계별 종료 조건은 [검증·개발 순서](06-validation-delivery.md)를 따른다.

## 접근 한계와 사용자 확인 질문

이 조사는 제품 소개와 공지 문서의 범위를 비교한 데 그친다. 제품을 실제로 가입해 유료벽을 우회하거나 결제 화면을 진행하지 않았고, 투두메이트 계정/구독의 크로스플랫폼 이용약관도 찾지 못했다. App Store 설명은 기능을 축약할 수 있으며, 제품에 언급이 없다고 해서 해당 기능이 반드시 없다는 뜻은 아니다. 공개 리뷰는 각 서비스 사용자 전체의 불편 빈도를 대표하지 않는다. 공식 일정 공고 5건은 서로 다른 대학/기관에서 실제로 여러 시각과 후속 기한을 요구한다는 사례이지, 국내 전체 학사 일정의 통계 표본은 아니다. 가격은 현지 스토어의 순간 표기다. 실제 첨부한 화면은 투두메이트 Mac 두 장으로 한정한다. Structured 화면 파일 확보는 브라우저 세션 접근 오류로 완료하지 못했으므로 해당 제품은 공개 설명과 상품 페이지를 참고한 범위로 기록한다.

사용자 테스트에서 먼저 확인할 질문은 다음과 같다.

- 수강신청이나 지원 창을 등록할 때 시작/마감 시각, 로그인 오픈, 추가 제출 마감을 한 흐름으로 보길 원하는가, 각각 별개 항목으로 보길 원하는가?
- 원하는 사전 알림은 “시작 전 몇 분”, “창이 열린 순간”, “마감 전” 중 무엇이며, 하나의 창에 몇 개가 적절한가?
- 기간 경과 표시를 작업 시작 전·중·후에 어떻게 읽는가? 숫자/원형 표시가 완료율로 오해되는가?
- 1회 ICS 가져오기 후 일정이 수정되었을 때, 기존 수동 편집과 새 파일 간 중복·충돌 선택을 사용자가 이해하고 처리할 수 있는가?
- 오프라인 작업을 여러 기기에서 바꾼 경우, 자동 승격·최신본 선택보다 충돌을 보존하고 고르게 하는 방식이 안전하다고 느끼는가?
- 투두메이트의 데스크톱 유료 경험은 어떤 기능, 구매 경로, 로그인 계정에서 발생했는가? 이 경험은 시장 가격 경쟁 분석과 별도 항목으로 검증한다.
- 실제 사용자가 앱을 열어 두지 않는 시간에도 시작·마감 알림을 기대하는가? 첫 버전의 앱 내 알림과 이후 푸시 제공 경계는 알림 실패 기대를 함께 검증해야 한다.
