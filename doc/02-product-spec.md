# 제품 요구사항 — 학생용 캘린더·D-Day

작성일: 2026-10-03 · 상태: 제품·시간·동기화 규칙 확정, 홈 시안 배치 선택 대기

## 1. 제품 목적과 성공 기준

맥에서 계획하고 아이폰에서 확인·수정할 수 있는 개인 일정 도구를 만든다. 사용자가 경험한 투두메이트 데스크톱 유료 정책이 출발점이다. 단순히 할 일을 체크하는 데 더해, 과제·논문·연구비의 제출 마감과 수강신청·티켓팅의 접수 시작을 구분해 보여준다.

일정의 시작 시각, 마감 시각, 남은 기간을 서로 다른 정보로 읽을 수 있어야 한다. 기간 바가 많이 찼다는 이유로 논문이나 과제가 많이 끝났다고 오해하지 않도록 한다. 같은 계정의 두 기기에서 변경 내용이 연결되고, 오프라인 수정이 조용히 사라지지 않는 것이 핵심 성공 기준이다.

실제 초기 사용량은 본인 한 명, 기기는 맥과 아이폰을 기준으로 한다. 주변 학생도 가입할 수 있으므로 인증과 계정별 데이터 격리는 처음부터 포함한다. 공동 일정 편집이나 조직 운영은 첫 버전의 대상이 아니다.

Next.js 16은 초기 Next.js 14 요구를 검토한 뒤 승인한 변경이다. 2026-10-03 확인한 공식 정책은 16.x를 Active LTS, 15.x를 Maintenance LTS, 14.x를 지원 종료 버전으로 표시한다. 실제 구현 시작 시 지원 버전과 최신 안정 패치를 다시 확인한다. [Next.js 공식 지원 정책](https://nextjs.org/support-policy).

## 3. 핵심 사용 시나리오

| 시나리오 | 등록하는 정보 | 사용자가 확인/수행하는 일 |
|---|---|---|
| 대학생 과제 | 과제명, 제출 날짜 또는 정확한 마감, 선택적 착수일, 수업 분류 | D-Day와 남은 시간 확인, 제출 후 완료 |
| 대학원생 논문 초안 | 준비 시작, 제출 마감, 메모·원문 링크 | 기간이 얼마나 경과했는지 확인, 별도 할 일 체크 |
| 국가 연구비 신청 | 연구책임자 제출과 기관 승인 각각의 마감 | 서로 다른 기한을 각각 등록해 놓치지 않기 |
| 수강신청 | 접수 시작·종료, 시간대, 신청 페이지 | 시작 전 카운트다운, 접수 중/종료 상태 확인 |
| 티켓팅 | 정확한 오픈 시각, 알 수 있으면 종료 시각, 예매 링크 | 앱을 열고 시작까지 남은 시간과 링크 확인 |
| 기기 이동 | 맥에서 등록한 일정 | 아이폰에서 같은 계정으로 확인·완료 |
| 오프라인 수정 | 캐시된 항목과 기기에 저장된 변경 | 앱을 다시 열어도 변경이 남고 재연결 후 반영 |
| 수정 충돌 | 두 기기가 같은 항목의 같은 기준 revision을 수정 | 서버 값과 내 수정을 비교하고 선택 |

연구비·논문처럼 여러 단계가 있는 절차는 첫 버전에서 각각의 기한과 관련 할 일을 수동으로 등록한다. 자동 선행 조건, 가중 작업 진척률, 프로젝트 간 의존성 엔진은 후속 검증 대상이다.

## 4. 일정 유형과 상태

| 사용자 작성 유형 | 저장 의미 | 정보와 상태 | 기본 노출 |
|---|---|---|---|
| 하루 할 일 | `task` | 제목, 날짜 선택, 선택적 마감; 미완료/완료 | 날짜가 있으면 홈의 해당 월간 칸과 선택 날짜 목록. 날짜 미정은 할 일 목록 |
| 기간형 마감 | `deadline` | 제목, 마감 날짜 또는 시각, 선택적 시작, 하위 체크리스트; 제출 완료는 별도 기록 | 홈 상단 기간 요약과 별도 캘린더. 월간 할 일 칸에는 넣지 않음 |
| 기간형 신청 | `window` | 제목, 시작 날짜 또는 시각, 종료는 알 때 입력, 하위 체크리스트; 신청 완료는 별도 기록 | 홈 상단 기간 요약과 별도 캘린더. 월간 할 일 칸에는 넣지 않음 |
| 고정 일정 | `event` | 제목, 시작과 종료 날짜 또는 시각; 완료 체크 없음 | 별도 캘린더에 표시하고 홈의 할 일 칸/목록에는 넣지 않음 |

`하루 할 일`, `기간형 마감`, `기간형 신청`, `고정 일정`은 입력 흐름의 이름이다. 저장 계약은 기존 네 종류를 유지한다. 기간형 항목의 체크리스트 완료 상태는 제출/신청 자체의 완료 상태와 다른 값이다. 화면에서는 `하위 할 일 · 미완료(남은 수/전체 수)` 또는 `하위 할 일 · 완료`로 표시해 혼동을 막는다. 하위 할 일이 없으면 체크리스트 상태를 표시하지 않는다. 한 개일 때는 `미완료` 또는 `완료`, 두 개 이상일 때 일부가 남아 있으면 `미완료(n/m)`(n=남은 수, m=전체 수), 전부 끝났을 때는 `완료`로 표시한다. 완료 뒤 항목을 추가하면 이 파생 상태는 자동으로 미완료가 된다.

날짜로 입력한 신청 기간은 종료 날짜까지 입력한다. 종료 시각을 알 수 없는 정시 오픈은 시작 시각만 있는 시간형 신청 항목으로 등록할 수 있다. 이때 종료 상태와 기간 바를 추측하지 않고 `종료 시각 미정`을 표시한다.

완료는 사용자의 실제 행동 기록이다. 시간이 끝나도 할 일·제출·신청이 자동으로 완료되지 않는다. 사용자가 신청 완료를 체크해도 원래 접수 시작·종료 시각은 유지한다. 삭제는 동기화 시 복구되지 않도록 revision이 있는 tombstone으로 처리한다.

## 6. 시간과 기간 계산 규칙

### 날짜와 시각

날짜 전용 값은 `YYYY-MM-DD`로 보존하며 임의로 UTC 자정에 저장하지 않는다. 정확한 시각은 UTC instant와 IANA 시간대 이름을 함께 보존한다. 기본 화면 표시는 항목의 시간대를 기준으로 하고, 기본값과 다른 시간대는 옆에 이름을 표시한다. 기기 시간대가 달라져도 입력한 행사 시각과 기준 시간대는 바뀌지 않는다.

날짜형 기간의 종료 날짜는 포함한다. 계산할 때 시작일 현지 00:00부터 종료일 다음 날 현지 00:00 직전까지로 해석한다. 시간형 기간은 시작 포함·종료 제외이며, 신청은 종료 시각에 닫힌 상태가 된다. 날짜형/시간형 모두 종료가 시작보다 앞서는 입력은 거부한다.

### D-Day

항목 시간대의 목표 달력 날짜에서 오늘 달력 날짜를 뺀다. 목표 날짜가 오늘이면 `D-Day`, 미래면 `D-N`, 과거면 `D+N`이다. DST가 있는 지역에서 하루를 항상 86,400,000ms로 나누는 구현을 사용하지 않는다. 시간형 항목의 마감 시각이 이미 지났으면 같은 날이더라도 `기한 경과`와 정확한 시각을 표시한다.

### 기간 바

시작과 종료를 instant로 해석한 뒤 `clamp((현재 - 시작) / (종료 - 시작), 0, 1)`로 계산한다. 반올림 정수 백분율은 접근성 설명과 검증에 사용하되 홈 진행 요약에는 숫자로 중복 표시하지 않는다. 날짜형은 위의 종료 날짜 포함 규칙으로 해석한다. 시작 전 0%, 종료 시점 이후 100%이며 작업 완료 여부가 수식에 들어가지 않는다.

시작 없는 마감에는 D-Day/남은 시간만, 종료 없는 오픈에는 시작 카운트다운을 표시한다. 현재 Figma의 종료 미정 시작 전 중립 레일은 시작 표시이며 시간 경과율이 아니다. 종료가 없는 항목에 퍼센트나 progressbar 접근성 값을 만들지 않으며 시작 후에는 레일을 숨긴다. 시작이 있는 기간형 항목은 카운트다운 표시가 기본 활성화되고 기본 노출 시점은 시작 1일 전이다. 사용자는 항목별 표시를 끄거나 0~30일 전으로 조정할 수 있다. 정확한 시간형은 시작까지 24시간 이상이면 `D-N`, 24시간 미만이면 `HH:MM`, 10분 미만이면 `MM:SS`로 남은 시간을 표시한다. 날짜형은 시작 날짜까지 달력 `D-N`을 표시하고 정확한 시각·초를 추정하지 않는다. 시작 경계에 도달하면 미래 카운트다운을 끝내고 기간 상태로 전환한다. 앱이 백그라운드였던 동안 초 단위 전달이나 예약 알림은 보장하지 않는다.

구현 구체화: 시간형의 N일 전은 N×24시간 전이며 D-N은 남은 실제 기간 올림이다. 날짜형의 N일 전은 시작 날짜에서 N달력일을 뺀 날짜다. 0일은 시작 전 표시 없음이다. 표시 반올림·DST·동기화 API를 포함한 정확한 구현 계약은 [핵심 구현 설계](implementation/04-core-implementation.md)에 있다.

기간 길이가 0인 시간형 입력은 거부한다. 시각적으로는 기간 바와 시작/종료 날짜·시각만 보여주고 `68% 경과`나 `6일 남음` 같은 반복 문구를 붙이지 않는다. 스크린 리더의 바 설명에는 `기간 경과 68%`처럼 의미를 포함한다. 하위 체크리스트 상태는 바 우측에 짧은 텍스트로만 별도 표시하고 체크박스를 반복하지 않는다.

### 홈 기간 요약과 임박 목록

홈 요약은 앞으로 7일 이내만 보여주는 알림 큐와 다르다. 등록된 미완료 `deadline`/`window` 중 최대 세 개를 다음으로 중요한 시각 경계가 가까운 순서로 표시한다. 시작이 미래인 `deadline`/`window`는 시작 시각, 진행 중인 `deadline`은 마감 시각/날짜, 진행 중이며 종료를 아는 `window`는 종료 시각을 정렬 기준으로 삼는다. 기한 경과 항목은 미래·진행 중인 경계보다 뒤에 두고, 남은 자리가 있을 때 최근에 경과한 항목부터 표시한다. 진행 중이며 종료를 모르는 신청 기간은 정렬 가능한 미래 경계가 있는 항목 뒤에 둔다. 완료 항목은 홈 요약에서 제외한다. 초과분은 홈을 밀어내지 않는 3열 오버레이에서 확인한다.

홈의 세 카드 요약은 자동 회전하거나 시간이 지날 때마다 위로 밀어 교체하지 않는다. 카운트다운 숫자는 현재 카드 안에서 갱신하고, 정렬 순서는 시작/종료 상태가 바뀌거나 항목을 수정·완료하는 등 의미 있는 상태 변화에서만 다시 계산한다. 이렇게 하면 읽는 중 항목이 사라지지 않으면서 가까운 접수 시작·마감을 우선할 수 있다. 초과 미완료 기간이 있으면 `더 보기` 버튼에 개수를 표시하고, 누르면 홈을 밀지 않는 오버레이에 긴급 순서의 전체 미완료 기간을 3열 격자로 표시한다. 전체 기간 상태 조회는 별도 `/calendar`에서 제공하며 데이터 필드가 아닌 기존 UID별 항목 snapshot에서 계산한다.

별도 캘린더의 기간 목록은 알림 큐가 아니다. 예정·진행·기한 경과·완료 그룹을 표시해 사용자가 전체 기간을 탐색한다. 기간 시작 카운트다운 표시와 별개로 기기 알림을 설정에서 선택할 수 있으며 기본은 꺼짐이다. Firebase가 없는 로컬 preview에서만 각 항목의 기준 시각·10분·1시간·24시간 전을 browser notification으로 앱 실행 중 확인한다. Firebase item 계약, 닫힌 앱 예약과 서버 알림은 후속 범위다.

## 7. ICS 가져오기 범위

첫 버전은 파일 선택 기반 일회성 가져오기다. 파일 자체를 서버 Storage에 올리지 않고 브라우저에서 읽어 미리보기한 뒤 선택한 일정만 Firestore에 저장한다.

지원 대상은 `VEVENT`의 제목, 시작·종료, 종일 날짜, UTC/IANA 시간대, 메모·URL, 일/주/월/년 반복과 제외일이다. 반복은 사용자가 선택한 가져오기 범위에서 개별 일정으로 펼치며 기본은 가져오는 날부터 6개월, 선택 가능한 최대 범위는 12개월이다. 가져온 개별 일정 수정은 외부 원본에 반영되지 않는다. 복잡한 사용자 정의 시간대, 해석 불가능한 반복 예외, `VTODO` 등 지원하지 않는 구성은 항목별 이유를 표시해 제외한다.

반복의 V1 부분집합은 `FREQ=DAILY/WEEKLY/MONTHLY/YEARLY`, 양수 `INTERVAL`, `COUNT` 또는 `UNTIL`, 주간의 요일 목록 `BYDAY`(서수 없음), 월간의 양수 `BYMONTHDAY`, 연간의 `BYMONTH`·양수 `BYMONTHDAY`, `EXDATE`로 정의한다. 명시하지 않은 월/일/시각은 DTSTART를 따른다. 존재하지 않는 월 날짜는 RFC 방식대로 발생하지 않으며 마지막 날로 임의 이동하지 않는다. 서수가 붙은 BYDAY, BYSETPOS, 여러 RRULE, RDATE, RECURRENCE-ID로 바뀐 예외 등은 해당 시리즈를 오류로 표시한다. 반복 예외가 지원되지 않을 때 기본 시리즈만 가져와 잘못된 일정을 만드는 것도 금지한다. 세부 표준 해석은 [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html)를 따른다.

원본 UID와 반복 발생 기준을 유지해 같은 파일의 재가져오기 중복을 판별한다. 변경된 원본은 자동 덮어쓰기하지 않고 미리보기에서 차이를 보여준다. 제목·시간이 비슷하더라도 원본 UID가 다른 항목을 임의로 합치지 않는다. 제안 입력 한도는 파일 5MiB, 펼친 발생 2,000개이며 초과 시 기간을 줄이도록 안내한다. 이 한도는 공급자 제한이 아니라 첫 버전의 제품 기본값이다.

## 8. 저장과 충돌 경험

`저장`은 기기에 안전하게 보존하는 것과 서버에 반영하는 것을 구분한다. IndexedDB 쓰기가 실패하면 저장 성공 표시를 하지 않는다. 온라인에서도 로컬 변경을 먼저 남기고 서버 반영을 시도한다. 처음 로그인과 캐시하지 않은 데이터 조회에는 연결이 필요하다.

재연결 시 서버 revision과 수정 전 기준 revision이 같을 때만 반영한다. 다르면 항목 전체를 충돌로 처리한다. 서로 다른 필드를 바꿨더라도 첫 버전은 자동 병합하지 않는다. 비교 화면에 원격 값과 내 수정, 바뀐 시간 필드를 명확히 보여주고 사용자가 선택한다. 다른 기기에서 삭제했다면 같은 ID로 되살리지 않고 서버 삭제 유지 또는 새 항목으로 내 수정 보존을 선택한다.

로그아웃이나 계정 변경 시 미전송 변경을 알리고 동기화/내보내기/기기에 보존 중 하나를 선택하도록 한다. 이전 계정의 초안이 다음 계정에 표시되거나 전송되지 않는다. 세부 처리와 멱등성 계약은 [Firebase·동기화 설계](04-firebase-data-sync.md)를 따른다.

## 9. 첫 버전 이후의 경계

| 단계 | 포함 | 진입 조건 |
|---|---|---|
| V1 무료 PWA | 캘린더, 할 일, D-Day, 기간 바, ICS, 계정 동기화, 오프라인·충돌, 인앱 안내 | 이 문서와 검증 문서의 수용 기준 |
| V2 iOS 네이티브 | 기기 로컬 예약 알림, 위젯, 같은 데이터 계약 | PWA에서 닫힌 앱 알림/빠른 확인 필요성 확인 |
| 선택적 서버 알림 단계 | Blaze 예약 함수와 Web Push/FCM, 수정·취소·재시도 | 알림 수요와 운영 비용을 별도로 검토한 뒤 선택 |
| 후속 제품 확장 | 외부 캘린더 연동, 복잡한 반복 편집, 연구 마일스톤 | 실제 사용 사례와 추가 범위 검토 |

첫 버전에는 그룹·친구 피드·결제·AI 추천·학교 공지 자동 수집·예매 자동화가 없다. 원문과 신청 페이지 링크는 사용자가 직접 기록한다. 정확한 초 단위 알림 도착, 브라우저를 닫은 상태의 알림, 오프라인 상태의 다른 기기 즉시 반영은 보장하지 않는다.

## 10. 베타에서 확인할 제품 가설

기간 바가 준비 행동을 돕는지, 시작 시각을 분리한 표시가 접수 기회를 알아채는 데 도움이 되는지, 두 기기의 저장 상태가 신뢰를 주는지 확인한다. 숫자 DAU를 목표로 삼기보다 본인 2주 사용 기록과 선택적인 주변 학생 사용 관찰로 시작한다. 사용자 관찰에서 확인하지 않은 시장 규모나 경쟁 제품 기능 부재를 성과처럼 주장하지 않는다.

성공 판단은 로컬 미리보기에서 대표 일정 네 종류를 등록·수정·완료·재정렬하고, 기기 알림을 사용자가 선택해 기준 시각을 이해하는 것이다. 이후 Firebase 단계에서는 맥→아이폰 확인·완료, 오프라인 수정 복구, 충돌 해결을 검증한다. 실제 실패와 불편을 기록하며, 시작 카운트다운의 발견 가능성과 정확성을 확인한다.
