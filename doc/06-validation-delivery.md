# 검증·개발 순서·운영 기준

작성일: 2026-10-03 · 상태: 승인된 제품 기준 + 구현 기본값 검토 제안

## 1. 이번 산출물과 구현 완료를 구분한다

이전 설계 단계의 산출물은 한국어 제품 설계 문서 7개, 출처를 기록한 공개 제품 화면, 월간 홈 시안과 선택된 1번 방향을 담은 편집 가능한 Figma 데스크톱·iOS 화면이다. 사용자가 다듬은 흰 배경 Figma를 바탕으로 Next.js 16 정적 PWA의 홈·캘린더·할 일·설정, Firebase Auth/Firestore repository·Rules·오프라인 충돌, ICS 미리보기·가져오기, JSON 백업, PWA 업데이트를 구현했다. 코드 자동 검증과 Chromium E2E는 통과했으며 실제 Firebase 프로젝트 연결·Google OAuth·iOS 실기기 확인은 별도다. 상세 결과와 Figma viewport 캡처는 [검증 보고](implementation/verification.md)에 있다.

초기 설계 시점에는 앱 소스와 package.json이 없어 `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`가 모두 `ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND`로 끝났다. 이후 manifest와 코드 scaffold가 추가되어 이 과거 결과는 현재 검증 상태를 설명하지 않는다. 현재 코드의 실제 test·typecheck·lint·build·E2E 결과는 [구현 검증 보고](implementation/verification.md)에 따로 기록했다. 문서 검사는 앱 동작 테스트를 대신하지 않는다.

| SYNC-02 | 연결 차단 후 추가·수정·완료·삭제 | 먼저 IndexedDB 성공, 서버 대기 표시 |
| SYNC-03 | 오프라인 수정 후 페이지/PWA 재실행 | 캐시와 로컬 초안 복원; 변경이 사라지지 않음 |
| SYNC-04 | IndexedDB 쓰기 실패 또는 저장 공간 부족 | 성공 알림 없음; 입력 유지, 재시도/내보내기 안내 |
| SYNC-05 | 두 기기가 같은 base revision 수정 후 순서대로 연결 | 첫 변경 반영; 두 번째는 원격/로컬 값을 보존한 충돌 |
| SYNC-06 | 제목과 마감 등 서로 다른 필드 변경 | 문서 revision이 바뀌었으므로 자동 병합 없이 선택 |
| SYNC-07 | 서버 commit 직후 응답 상실, 다른 기기 추가 수정, 원래 요청 재시도 | immutable receipt로 이미 적용됨 인식; 중복 생성/revision 증가 없음 |
| SYNC-08 | 오프라인 수정 중 원격 삭제 | 기존 ID 부활 없음; 삭제 유지 또는 새 ID로 내 내용 보존 |
| SYNC-09 | 충돌 해결 선택 뒤 원격이 다시 수정 | 새 충돌을 다시 보여줌; 선택한 초안도 보존 |
| SYNC-10 | 서버 snapshot 미수신/캐시/동기화 대기/실패 | 상태를 구분; 캐시를 최신 서버 값이라고 표시하지 않음 |
| SYNC-11 | 기간 하위 할 일을 오프라인에서 체크, 다른 기기에서 같은 기간을 변경 | checklist를 부모 snapshot으로 보존하고 revision 충돌에서 자동 병합 없이 두 판본 표시 |
| SYNC-12 | 두 탭에서 같은 localSequence로 저장, 뒤늦은 폼 저장 | IndexedDB CAS로 후행 저장을 stale-local로 거부; 앞선 수정과 후행 입력 모두 보존 |
| SYNC-13 | 송신 중 successor 편집, ACK 유실 후 원격 추가 수정 | ACK는 해당 operation만 처리; successor base는 predecessor receipt revision이며 최신 원격 revision으로 자동 rebase하지 않음 |

추가 회귀 조건: 신규 항목을 송신 전에 삭제하면 서버에 불필요한 항목을 만들지 않는다. 생성 송신 중 삭제는 receipt로 결과를 확인한 뒤 처리한다. ICS 재가져오기는 tombstone을 부활시키지 않으며 교체 미리보기 뒤 다른 기기가 변경한 경우 충돌을 보존한다. UID 전환 뒤 이전 요청의 늦은 응답도 새 계정에 표시되지 않는다.

송신 중 추가 편집, 동일 항목의 여러 오프라인 수정, IndexedDB ack 처리 중 앱 종료, 두 브라우저 탭의 중복 전송도 검증한다. journal의 고정된 송신 snapshot과 receipt가 일치해야 하며 뒤에 작성한 초안을 이전 ack로 삭제하면 안 된다.

## 4. 구현 순서와 단계 종료 조건

| 단계 | 작업 | 종료 조건 |
|---|---|---|
| 0 | 문서와 시각안 검토 | 기능 계약 검토, 사용자 선택 시안의 데스크톱·모바일 Figma 프레임 확인 |
| 1 | 정적 Next 앱·Firebase Emulator·테스트 명령 | 정적 build 성공; Auth/Rules 분리 테스트 가능 |
| 2 | 시간 모델·repository·revision/receipt·journal | DATA/TIME/AUTH/SYNC 핵심 실패 시나리오 통과 |
| 3 | 캘린더·상세·할 일·상태 UI | 선택한 시안에 맞춰 반응형·접근성 핵심 흐름 동작 |
| 4 | ICS 미리보기·중복 처리·내보내기 | 부분 실패·재시도 포함 ICS/DATA-05 통과 |
| 5 | 전경 카운트다운·선택적 로컬 알림·PWA 캐시 | 카운트다운과 알림을 분리; 알림 기본 꺼짐, 앱을 열었을 때만 확인; Firebase·닫힌 앱 예약은 후속 범위 |
| 6 | 실기기 검증·무료 베타 | 맥↔아이폰 흐름, 데이터 격리와 필수 명령 성공 |

메모리 저장소만으로 오프라인 지원을 완료했다고 간주하지 않는다. 필드 표시만 만들고 ICS 파싱·충돌 해결·신청 링크 같은 핵심 동작을 생략하지 않는다. 단계별 기능을 줄여야 하면 영향받는 FR/수용 기준과 이유를 문서와 함께 변경한다.

필수 명령은 `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`다. Next.js 16의 lint 스크립트는 ESLint CLI를 호출하도록 정의하며 오래된 `next lint`를 전제하지 않는다. 테스트 도구 후보는 `[ASSUMPTION]`으로 검토하고 실제 생성한 scripts를 기준으로 확인한다.

사용자 지시대로 TDD는 시간/DST·보안 규칙·멱등 트랜잭션·오프라인 동기화·ICS 반복/시간대/재시도의 어려운 작업에만 적용한다. ICS 오류는 날짜 이동과 가져오기 중복·유실을 만들 수 있어 데이터 무결성 고위험 계약이다. 화면·일반 CRUD·PWA 조립은 먼저 구현하고 필요한 실패 조건·사용자 흐름을 검증한다. 쉽게 되돌릴 수 있는 스타일 변경과 설정 값을 복제하는 테스트는 작성하지 않는다. 상세 작업 배정은 [실행 계획](implementation/06-execution-plan.md)이 기준이다.

Emulator 단위/통합 테스트와 브라우저 테스트로 자동화할 수 있는 계약을 먼저 검증한다. iOS 설치·저장 지속성·로그인 복귀·백그라운드 복귀는 실기기에서도 확인한다. 공급자 API 설명만으로 두 기기 검증을 완료했다고 하지 않는다.

## 5. 무료 운영과 데이터 보관

초기에는 Firebase Spark의 Hosting/Auth/Firestore를 사용한다. App Hosting, Functions, Cloud Storage 첨부 파일, 서버 cron을 첫 버전의 필수 운영 서비스로 넣지 않는다. 공급자 무료 한도는 배포 시 다시 확인한다. 한 명의 소규모 데이터에서는 UID별 일정 컬렉션 listener 하나를 공유하고 화면의 기간·임박 목록을 메모리에서 필터링한다. 화면마다 구독을 중복하지 않고 receipt 컬렉션 전체는 구독하지 않는다. 항목 수와 읽기량이 커지면 범위 쿼리·인덱스 전환을 먼저 검증한다.

2026-10-03 확인한 [Firebase 공식 가격표](https://firebase.google.com/pricing)의 Spark/Standard 기준은 다음과 같다. 프로젝트 전체의 한도이며 학생 계정마다 새 한도를 받는 구조가 아니다.

| 서비스 | 확인한 무상 한도 | 설계에 미치는 영향 |
|---|---|---|
| Firestore Standard | 저장 1GiB, 읽기 50,000/일, 쓰기 20,000/일, 삭제 20,000/일, 전송 10GiB/월 | 항목 변경과 receipt가 각각 쓰기를 사용; 재접속·Rules 추가 읽기·트랜잭션 재시도도 관찰 |
| Firebase Hosting | 저장 10GB, 전송 360MB/일 | 앱 정적 자산 크기·캐시를 관리; 개인 무료 베타로 제한 |
| Auth Google 로그인 | 일반 인증 서비스 Spark 사용 가능 | 전화/SMS 인증·Identity Platform의 별도 조건을 혼합하지 않음 |

예를 들어 캐시를 활용하지 못한 초기 읽기가 2,000개라면 10회의 새 구독은 문서 읽기 약 20,000회에 해당한다. Rules와 다른 작업의 비용은 이 단순 예시에 포함하지 않았다. 무료 운영은 사용자 수만으로 보장되지 않으므로 실제 콘솔 지표를 기준으로 판단한다.

콘솔에서 읽기·쓰기·저장·Hosting 전송량을 확인한다. 베타 기본 경고 기준은 하루 한도 또는 저장 한도의 70% 사용이며 90%에 도달하면 원인과 조회 범위를 검토한다. Spark에서는 자동 유료 전환을 전제하지 않고 quota 실패를 상태 UI와 재시도 정책으로 처리한다. 브라우저 복귀 시 무한 재시도하거나 1초마다 서버를 조회해 카운트다운을 구현하지 않는다.

데이터는 Firestore canonical 항목, 불변 operation receipt, tombstone과 로컬 journal로 나뉜다. receipt/tombstone은 V1에서 자동 삭제하지 않는다. 한 명 기준 보관량을 관찰하고 한도에 가까워지면 오프라인 기기의 미전송 변경까지 고려한 보관/정리 설계를 별도 결정한다. 본인 JSON 내보내기를 제공하지만 자동 재해 복구나 공급자 백업을 대신한다고 설명하지 않는다.

로그인은 최소 정보만 사용하고 캘린더·연락처 OAuth 권한을 추가 요청하지 않는다. 제품 로그에 일정 제목·메모·토큰을 남기지 않으며 동기화 오류 코드와 비식별 진단을 사용한다. 공유 기기에서는 영구 캐시 사용 여부를 설명하고 계정 전환 때 로컬 데이터 경계를 확인한다.

## 6. AGENTS.md와 설정 변경 제안

아래는 설계 당시 AGENTS.md에 남아 있던 셋업을 제품 방향에 맞게 바꾸기 위한 제안 기록이다. 구현 단계에서 Node/pnpm pin, Firebase Emulator와 JDK 21, 실제 package scripts, repository 경계를 반영했고 현재 저장소의 AGENTS.md와 README가 기준이다.

| 현재 안내/규칙 | 제안 | 유지할 의도 |
|---|---|---|
| `pnpm prisma migrate dev` | Firebase Auth/Firestore Emulator 시작과 Rules/인덱스 관리 명령으로 교체 | 재현 가능한 로컬 데이터 환경 |
| `.env.example` → `.env.local` | 실제 구현 때 Firebase 공개 설정 항목 예시 추가; 비밀 값은 파일에 쓰지 않음 | 환경변수 관리, .env 미커밋 |
| DB 접근은 repository.ts | Firestore·IndexedDB 접근도 repository 경계로 집중 | UI와 저장 구현 분리 |
| API 오류는 ErrorResponse | V1은 동적 HTTP API 없음; 이후 도입한 API에 그대로 적용 | 오류 계약 일관성 |
| `src/payments/` 별도 인증 | 결제 모듈을 만들지 않음; 향후 도입하면 해당 분리 규칙 유지 | 독립적인 인증 경계 |
| 새 production 의존성 PR 논의 | `[ASSUMPTION]` 후보·필요성·대안·라이선스를 먼저 기록 | 불필요한 의존성 추가 방지 |

후보는 Firebase Web SDK, ICS 파서, 필요 시 날짜/시간대 도구와 캘린더 렌더링 도구다. 네이티브 단계의 Expo/React Native/Notifications/로컬 저장 도구는 별도 후보다. 사용자가 선택한 플랫폼을 구현하는 데 필요한 패키지라도 기존 규칙에 따라 PR에서 후보를 명시하고 검토한다. 문서 작성만을 위해 프로덕션 의존성을 설치하지 않는다.

실제 배포는 별도 단계에서 수행한다. main push가 배포라는 기존 안내를 존중하므로 문서 작업에서 임의로 push하지 않는다. 향후 CI는 검증 성공 후 정적 산출물과 Rules/인덱스를 명시적으로 배포하고 실패한 버전은 공개하지 않는다.

## 7. 문서 자체의 검증

완료 전에 필수 문서 7개, 자료 기록 문서와 새 시안 3개, 이전 시안·참고 이미지와 출처/프롬프트 기록의 존재를 확인한다. 상대 링크와 로컬 이미지 경로, Markdown 코드 fence와 표 구조를 확인하고 `FR-01`~`FR-16`의 설계·검증 연결을 검토한다.

특히 아래 사항이 모든 문서에서 일치해야 한다.

- Spark 첫 버전에 Functions/서버 예약 푸시/동적 Next API가 필수로 섞여 있지 않다.
- 기간 바는 시간 경과율이고 하위 체크 상태는 별도 표기다. 홈에는 다음 관련 시간 경계가 가까운 미완료 기간 최대 세 개를 표시하며 자동 회전하지 않는다; 초과분은 캘린더를 밀지 않는 3열 오버레이에서 확인한다.
- 기기 알림은 설정에서 켜야 사용할 수 있고 기본은 꺼져 있다; 저장 범위는 현재 브라우저이며 닫힌 앱 예약은 제공하지 않는다.
- 홈은 모바일에서도 월간 할 일 그리드, 기간 요약, 선택 날짜 할 일의 순서를 유지한다. 주간·월간 전체 일정과 고정 일정은 별도 캘린더에서 본다.
- 충돌을 last-write-wins나 자동 필드 병합으로 처리하지 않는다.
- 멱등성을 마지막 operation ID 하나만으로 보장한다고 하지 않는다.
- 종료 미정 오픈, 날짜형 종료일 포함, 시간형 종료 시각의 경계가 일치한다.
- 텍스트 문서/시안의 계획과 실제 구현 완료를 혼동하지 않는다.

시각 방향은 1번 「경계 없는 월간」이며 Figma의 사용자가 다듬은 화면 구성을 기준으로 한다. 흰 배경·라벤더 포인트, 기간 2행과 초과분 전체 보기 동작이 프레임·문서와 맞는지 확인한다. 그 외 미정 기본값, 모순, 빠진 오류 처리, 출처 없는 현재 정책 주장 등을 찾아 고친다.

### 이전 제품 설계 단계의 확인 결과

2026-10-03 확인 결과: 필수 설계 문서 7개와 자산 기록을 포함한 Markdown 9개, 상대 파일 링크 42개, 외부 URL 95개를 확인했다. 링크·코드 fence·표 열 수 검사는 통과했고, FR-01~FR-16의 추적표 및 수용 시나리오가 연결되어 있다. PNG는 이전 시안 3개와 두 차례 월간 홈 시안 6개(총 9개), 참고 WebP는 2개다. 신규 PNG 세 장은 각각 1487×1058로 목표 1440×1024와 다르며 자산 기록에도 명시했다. 이 검사는 링크 구조를 확인한 것이며 외부 URL의 실시간 가용성 전체를 검증한 것은 아니다.

모델별 초안을 통합하면서 4종 일정 계약, 하루 할 일과 기간형 항목의 구분, 홈의 월간 할 일 구조, 모바일 순서, 기간 계산·날짜형 알림 기준, RRULE 부분집합·UID 누락 처리, journal 필수 저장, ACK/후속 초안·receipt, tombstone·재가져오기와 UID 전환 규칙을 대조했다. 문서에 없는 기능을 구현한 것으로 간주하거나 시안의 70% 예시를 정식 계산으로 사용하지 않는다.

2026-10-03 설계 시점에는 앱 manifest가 없어 검증 명령을 실행하지 않았다. 현재 구현의 검증은 [구현 검증 보고](implementation/verification.md)를 기준으로 한다. 최신 Figma 프레임은 1440×1024 데스크톱(185개 하위 레이어)과 390×844 iOS(170개 하위 레이어)다. 순백 배경·편집 가능한 텍스트·이미지 채움 0개를 확인했다. 실제 화면은 상단 기간 3개와 초과 기간 팝오버, 월간 할 일, 단일 추가 진입점, 중앙 아이콘 내비게이션을 기준으로 검증한다. 실제 Firebase/Google OAuth와 실기기 PWA 확인은 별도로 남아 있다.

### 구현 준비 단계의 검증 기록
