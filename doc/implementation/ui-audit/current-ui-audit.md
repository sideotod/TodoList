# 이전 데스크톱 UI 감사 기록

> 이 감사와 `*-after.png` 캡처는 앞선 프론트엔드 상태를 대상으로 작성했다. 이후 앱 셸을 840px로 고정하고 구성요소 코드를 다시 분리했으므로 아래의 사후 캡처를 현재 구현의 시각 검수 결과로 사용하지 않는다. 최신 관찰 결함·현재 코드 동작·남은 검수는 [09-ui-audit-and-component-behavior.md](../09-ui-audit-and-component-behavior.md)를 기준으로 갱신한다. 현재 코드의 새 캡처는 아직 저장하지 않았다.

감사일: 2026-10-05 · Asia/Seoul  
상태: 수정 전·후 캡처 완료 · 사후 검토 완료

## 1. 감사 범위

- 대상: 홈의 기간 요약·월간 할 일·선택 날짜 할 일, 기간 더 보기 오버레이, 별도 캘린더.
- 사용자 목표: TodoMate의 데스크톱 화면 크기에 맞춘 앱 같은 밀도에서 임박 기간과 당일 할 일을 빠르게 확인하고, 달력은 별도 화면에서 확인한다.
- 기준 화면: 현재 Chrome 미리보기 1512×790, TodoMate를 띄운 화면의 캡처 해상도 2000×1564.
- 데이터: 고정 디자인 fixture. TodoMate 창은 구독 안내가 떠 있어 화면 해상도만 참고했고, 계정/친구 화면은 제품 비교에 사용하지 않았다.
- 수정 전 캡처 실행: `node doc/implementation/ui-audit/capture.mjs`. 첫 실행은 기존 2026-10-03 디자인 미리보기, 날짜 선택, 할 일 순서와 완료 상태를 기준으로 삼았다. `*-before.png`는 구현 전 증거로 유지한다.

## 2. 단계별 관찰

### 1단계 — 홈 기본 상태

증거: [현재 브라우저 크기](evidence/01-home-before.png), [TodoMate 화면 크기](evidence/04-home-todomate-size-before.png)

- 좋은 점: 기간 카드 3개가 같은 크기로 정렬되고 제목, 상태, 진행 레일, 양 끝 날짜의 순서가 일관된다. 월간 달력과 선택 날짜 목록도 분리되어 있다.
- UX 위험: 1512×790에서 내용 폭은 1312px이며 문서 높이는 812px로 뷰포트보다 22px 길다. 화면 아래쪽에 세로 스크롤이 생긴다. 2000×1564에서는 내용 폭이 여전히 1312px이고 좌우 위치가 x=344~1656으로 고정되어, TodoMate 크기의 창 안에 앱이 작고 위쪽에 몰려 보이며 나머지 공간이 과도하게 비어 있다.
- 시각 문제: 예정 진행 레일 왼쪽의 8×8 원형 표식이 진행 바와 같은 높이에 놓여 작은 점처럼 보인다. 시작까지 남은 시간 레일에서는 시작 지점이 바의 오른쪽 끝이므로 이 점이 어느 시각을 뜻하는지 바로 이해하기 어렵다. 월간 날짜 아래의 작은 점도 의미를 설명하는 표시가 없어 장식 점처럼 보일 수 있다.
- 접근성 위험: 날짜 점과 예정 표식은 크기와 대비가 작다. 캡처만으로 실제 대비비율, 확대 시 reflow, 스크린리더 문맥을 확정할 수 없다.

### 2단계 — 기간 더 보기 오버레이

증거: [기간 전체 펼침](evidence/02-periods-expanded-before.png)

- 좋은 점: 여분의 기간 2개가 세 열 격자의 두 번째 줄에 들어가며 기존 달력과 할 일 영역을 아래로 밀지 않는다. 불투명한 흰 배경과 그림자가 뒤 화면과의 층을 구분한다.
- UX 위험: 첫 번째 줄 카드와 추가 카드가 같은 격자 안에 나타나므로 앞의 세 개가 대표이고 뒤의 두 개가 추가라는 관계는 순서에 의존한다. 긴 제목이나 상태가 들어올 때 줄바꿈 대신 말줄임으로 숨겨지는지 확인이 필요하다.
- 확인 결과: 캡처 상태에는 겹친 텍스트나 화면 밖으로 튀어나온 카드가 없다. 애니메이션 종료 뒤 다섯 카드가 모두 접근 가능한 영역으로 노출된다.
- 접근성 위험: 열림/닫힘 상태는 `aria-expanded`로 제공된다. 열릴 때 키보드 초점 이동, 모션 감소 설정, 화면 확대에 따른 팝오버 내부 스크롤은 별도 키보드·스크린리더 테스트가 필요하다.

### 3단계 — 별도 캘린더

증거: [캘린더 화면](evidence/03-calendar-before.png)

- 좋은 점: 날짜 띠와 선택 날짜의 시간순 일정 목록을 한 흐름으로 확인할 수 있다. 앱명이나 검색용 헤더는 없다.
- UX 위험: 캘린더 내용은 자체 폭 1000px에 제한된다. 넓은 TodoMate 화면에서는 홈과 마찬가지로 캘린더가 가운데 좁게 모일 수 있다. 홈의 기간 보드와 캘린더의 기간 목록으로 이동하는 경로·화면 폭을 함께 점검해야 한다.
- 접근성 위험: 화면 캡처는 달력 버튼의 키보드 순서나 뷰 전환 이름이 충분한지 증명하지 않는다.

## 4. 근거와 제한

- 눈으로 확인한 스크린샷은 이 감사 실행에서 저장한 파일만 사용했다. 이전 캡처는 근거로 사용하지 않았다.
- 위치·폭·높이는 Playwright의 viewport와 DOM bounding box로 확인했다. 픽셀 단위의 색 대비, 모든 중간 창 크기, 실제 VoiceOver 사용은 아직 검사하지 않았다.
- 수정 전에는 `?preview=design`의 샘플 편집이 실제 항목 저장과 연결되지 않았다. 이 감사 이후 Firebase를 제외한 CRUD·완료·순서·브라우저 알림 설정을 localStorage에 연결했으며, 실제 Firebase 로그인과 기기 간 동기화는 이번 감사 범위에서 제외했다.
- TodoMate 캡처는 구독 안내 창이 콘텐츠를 가리고 있어 2000×1564 해상도 참고에만 사용했다. 개인 프로필 정보가 있는 원본은 저장하거나 문서에 첨부하지 않았다.

추가 수정: 시작 전 레일의 모호한 원형 표식을 제거해 임의 점처럼 보이지 않게 했고, 달력의 일정 점은 7×7px로 키웠다. 화면 색 토큰은 Figma 기준 `#6E4DF5` 라벤더, `#211F30` 본문, `#596178` 보조 글자, `#E8E8F2` track에 맞췄다. 1000×780에서 선택한 날짜는 실제 실행일(Asia/Seoul)에 맞으며 월간 할 일과 실제 체크박스가 보인다.

회귀 확인으로 preview의 추가·수정·삭제·완료와 순서 저장, 마우스 홀드 재정렬, 알림 기본 꺼짐·설정 저장, 알림을 켠 뒤 지정 시각에 foreground 브라우저 알림을 1회 전달하는 흐름, 3개 기간 + 초과 목록을 Chromium E2E로 확인했다. 남은 제한은 시각 캡처만으로 VoiceOver/실제 화면 판독, 앱이 닫힌 상태의 OS 예약 알림, iOS 설치형 PWA 동작을 확정할 수 없다는 점이다. Firebase 동기화는 이번 로컬 데스크톱 단계의 대상에서 제외했다.
